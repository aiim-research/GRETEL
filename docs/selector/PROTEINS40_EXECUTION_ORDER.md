# Selector queue: PROTEINS, 40 random instances, 2000 minimizer oracle calls

Auto-managed by `scripts/run_revision_queue.py`. Each unchecked entry is a config, flipped to checked once `lab/output/results/<scope>/.../results_0_1.json` exists.

Protocol: fold 0, the 40 ids of `lab/config/snippets/proteins_40_instances.json`, DCE generator with its fixed internal seed (same starting counterfactual for every method), minimizer seed 0, `max_oracle_calls` 2000 for every method (plain LBS with `strict_budget`). Every learned selector starts cold: the checkpoints from the previous machine are parked in `models/prev-machine-2026-09-08/`. One worker, in series (the machine is shared), with `--gpu` because the PROTEINS oracle cache was written from a CUDA session and does not load with CUDA hidden. Configs generated by `scripts/gen_selector_sample_configs.py` (command in its docstring).

```
nohup ~/miniconda3/envs/GRTL/bin/python scripts/run_revision_queue.py --list docs/selector/PROTEINS40_EXECUTION_ORDER.md --workers 1 --gpu --timeout 21600 > lab/output/queue_proteins40.log 2>&1 &
```

Three arms per selector, so that each variant answers two questions:

1. How much does the model actually train during the run? The monitor CSV (`lab/output/selector_logs/selector_<tag>_PROTEINS-<hash>.csv`, one row per instance) records cumulative update steps and examples, the relative weight drift from the cold initialisation, loss EMAs and the prequential skill of the pre-registered move scores (v2 family; v1 has steps, examples, drift and per-phase calls and successes).
2. How much does that training improve the search? `learned` against `-frozen` (same seeded network, same proposal policy, never updated) isolates the effect of training; `-frozen` against `-random` (uniform proposals, same skeleton) is what an untrained ranking does by itself. Compared per instance on final GED, minimizer oracle calls and calls per accepted move in each phase, and as a trend over the 40 instances.

Order: the references first (plain LBS, thesis selector v1 and its frozen twin), then v2g and v2e as learned / frozen / random. The other v2 variants (v2, v2b, v2c, v2d, v2f) were dropped on 2026-09-30 after v1 and v2g showed no measurable effect of the model (they share the v2 selector and only change the skeleton); their configs stay in `lab/config/generate_minimize/proteins40/dce/`.

Selector v3 (added 2026-09-30, configs from `scripts/gen_selector_v3_configs.py`): the v2e skeleton unchanged (the study only touches the selector, never LBS). `v3-collect` ran uniform proposals on the 72 fold-0 test instances outside the evaluation set and dumped every scored example. On those examples `scripts/selector_offline_bench.py` picked the selector changes: P0 (scores standardised inside each candidate set, removal temperature 0.25) and training on the hard flip (`target: flip`). `scripts/pretrain_selector_v3.py` wrote `models/pretrained/edge_selector_v3-pre_PROTEINS.pt` (held-out removal AUC 0.756, skill +0.16). Arms: v3 (online from scratch), v3-frozen, v3-pre (pretrained plus online), v3-pre-frozen; the random reference is v2e-random. v3 stayed above v2e in GED because its near-greedy policy re-proposed the same cached candidates on every retry; v3b adds a tabu memory in the selector for that (only v3 and v3b run here so far).
