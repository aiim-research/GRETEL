# Protocol v2: experiments without padding

Protocol v2 (decided on 3 and 4 November 2026, task 0 of the research plan) runs every graph at its own size. In v1, variable-size datasets are padded with empty nodes up to the largest graph of the dataset. That made the oracles depend on the padding (a GCN that averages over all nodes reads the amount of padding: removing it changes the predicted class of 72 of 100 BBBP molecules), let the explainers edit nodes that do not exist (edges to padding rows flip the oracle: from 20 % to 50 % of the counterfactuals of AIDS, BBBP and PROTEINS in the selector study touched them) and kept the metrics from charging nodes. v2 removes the padding instead of patching around it.

v1 stays as it is. The same code runs both protocols, and nothing of v1 changes: every v2 feature is opt-in, and the v1 configs keep their hashes, their caches and their numbers.

## What v2 guarantees

- **Every node is real.** No AdjacencyMatrixPadder: a graph's matrix is its own size, the minimizers search only its node pairs, and the oracles never see padding (they are trained again, without it).
- **Isolated nodes.** On datasets whose graphs are connected by nature (every dataset but COLORS-3, Synthie and ASD), a node an edit leaves without edges is deleted: the oracle drops it before predicting, and the counterfactual is materialized without it, its node correspondence recording the deletion. These datasets also lose, when they load, the nodes that are already isolated (salt ions in BBBP, AIDS and Mutagenicity, the usual salt stripping). The manipulator `DeleteIsolatedNodes` declares the policy; without it (v1, and the three datasets above) isolated nodes stay.
- **Decoupled generation.** As in the first paper, each generator runs once per instance and fold, and every minimizer starts from the same seed. DCE and DCEM (`projection: "assignment"`) rank the dataset graphs of another class by the structural edit cost under a node correspondence (Hungarian assignment on node features and degree) and return the full projection of the nearest one the oracle accepts: the candidate's edges, node features and edge attributes on the input's nodes, the input's other nodes isolated and so deleted. A candidate no larger than the input is always accepted (its projection is the candidate itself, up to node names), so the generator's correctness is 1. If no candidate is accepted the generator falls back to the candidate itself, outside the input's nodes, which no minimizer can shrink (`seed_kind: "fallback"`). DCEM keeps one medoid per class and size (the medoid among the graphs of at most n nodes) and classifies with the oracle.
- **Minimizers inside the input's nodes.** Each minimizer searches its own space from the same seed: BLS edge edits on the input's node features (with its attribute methods when `attributed`), BLS-F (`local_search_features`, new) edge edits and node-feature substitutions towards the seed, OBS the reversal of the seed's edge edits. A minimizer that cannot improve returns the seed, which is valid.
- **A measure that charges nodes.** `src/utils/metrics/correspondence.py` defines the edit cost of a pair under an explicit node correspondence: node insertions and deletions, edge edits (incident edges of inserted or deleted nodes included) and the feature distance of the mapped nodes, with the costs as parameters. Its stages (`edit_distance.EditDistance`, `StructuralEditDistance`, `MatchedFeatureDistance`) run after the cell-wise GED, which stays for comparison with v1; the cell-wise FED, which needs equal sizes and matches nodes differently from the GED, leaves the v2 pipeline. This is the first step towards the unified metric of line B1, not that metric yet.
- **GCN oracles with the layers their config asks for** (`exact_conv_layers`; v1 builds at most two convolutions).

## What is v1 only

The explainers that need every graph at one size declare `requires_fixed_size` and stop with a clear error on a dataset of several sizes: RSGG, GCounteRGAN, EAGER, CLEAR, CF2, DDBS, and DFS and DBS (their priors are per node index). They keep running on padded datasets and on fixed-size ones (ASD, Tree-Cycles). DBS is out of the v2 configs until its prior is adapted.

## Where things are

- `lab/config/v2/`: the configs and the snippets they compose, generated by `scripts/gen_v2_configs.py` from the v1 configs of the first paper and of the selector paper (its docstring gives the transformation). Do not edit them: change the v1 config or the script and regenerate. Index: `CONFIGS.md`.
- **Oracles trained on a machine with a GPU are pickled with CUDA tensors and do not load on the server's CPU nodes.** Before committing any new oracle cache, run `python tools/resave_cache_cpu.py <files>` (it moves the model to the CPU and checks, in a process without CUDA, that the weights are bit-identical), or train it with `CUDA_VISIBLE_DEVICES=""`. The v2 oracles of 4 November were trained on the laptop's GPU and re-saved this way.
- Scopes, selector model tags, checkpoints and collections carry `v2-` or a `v2/` folder, so v2 never reads or overwrites a v1 artefact. The dataset and oracle caches separate by themselves, because their hashes change.
- The decisions and the analysis behind them: `phd/tareas/task-0/README.md` (outside this repository).
